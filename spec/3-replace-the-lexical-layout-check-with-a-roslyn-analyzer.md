# Replace the lexical layout check with a Roslyn analyzer

## Summary

The `layout` gate (`scripts/check_line_layout.py`) enforces line length and
wrapped-`)` placement by scanning text, so unusual code can fool it and it
cannot run in the IDE. This item replaces it with a Roslyn analyzer project
(`netstandard2.0`) that every project references through
`Directory.Build.props`, and which reports ordinary build errors. The same
analyzer also enforces four more house rules from
`docs/contribute/coding-standards.md` that today are reviewed by hand in C#
(block nesting, nested expressions, boolean-chain layout, no `Async` suffix),
matching the Python rules E9003, E9002 and E9004. The canary markers move from
`layout:` to `build:<ID>`, and the Python check, its gate, and its tests are
deleted.

## Acceptance criteria

Diagnostic IDs used below (all `DiagnosticSeverity.Error`, enabled by
default, category `Style`):

| ID | Rule |
| --- | --- |
| `ASWF001` | Line longer than 120 characters |
| `ASWF002` | Wrapped call or declaration whose `)` is not on its own line |
| `ASWF003` | Blocks nested too deeply |
| `ASWF004` | Expressions nested too deeply |
| `ASWF005` | Boolean chain of three or more not one operand per line |
| `ASWF006` | Method we declare has an `Async` suffix |

### Project and wiring

- **AC-1.** Given the repository, when it is inspected, then a project
  `src/AgenticSoftwareWorkflow.Analyzers` exists, targeting `netstandard2.0`,
  containing one `DiagnosticAnalyzer` (language `LanguageNames.CSharp`) per
  ID `ASWF001` to `ASWF006`.
- **AC-2.** Given `Directory.Build.props`, when any project other than the
  analyzer project itself is built, then it references the analyzer project
  as an analyzer (`OutputItemType="Analyzer"`,
  `ReferenceOutputAssembly="false"`), and the analyzer project does not
  reference itself.
- **AC-3.** Given any project under `src/` or `tests/`, when
  `dotnet build` runs, then a violation of any ID above fails the build with
  an error carrying that ID (not a warning), the same way IDE1006 does.
- **AC-4.** Given the repository as committed after this item, when
  `scripts/gates.sh` runs, then every `.cs` file under `src/` and `tests/`
  (other than the analyzer project) builds with no `ASWF` diagnostic. Existing
  code is fixed to comply; no rule, threshold, or `.editorconfig` setting is
  weakened to achieve this.
- **AC-5.** Given a file marked generated (`<auto-generated>` header, or a
  `.g.cs`/`.designer.cs` name, or `[GeneratedCode]` types), when it is
  compiled, then no `ASWF` diagnostic is reported for it.

### ASWF001: line length

- **AC-1a.** Given a source line of exactly 120 characters, when analyzed,
  then no `ASWF001` is reported.
- **AC-1b.** Given a source line of 121 characters, when analyzed, then one
  `ASWF001` is reported, located on that line, and its message states the
  length and the maximum (`121 characters (max 120)`).
- **AC-1c.** Given a line over 120 characters inside a comment, an XML doc
  comment, a string literal or a raw string literal, when analyzed, then
  `ASWF001` is reported for it, because the rule is about the line, not the
  token.
- **AC-1d.** Given a file with three over-long lines, when analyzed, then
  exactly three `ASWF001` diagnostics are reported, one per line, even where a
  line holds several tokens.
- **AC-1e.** Given a line containing a tab, when its length is counted, then
  the tab counts as one character, and the line terminator is not counted.

### ASWF002: wrapped `)` on its own line

- **AC-2a.** Given an invocation `Foo(a,` / `b)` whose argument list spans
  lines and whose `)` follows an argument on the same line, when analyzed,
  then one `ASWF002` is reported at the `)` token.
- **AC-2b.** Given the same call written with `)` as the first token on its
  own line, when analyzed, then no `ASWF002` is reported.
- **AC-2c.** Given an argument list on a single line, when analyzed, then no
  `ASWF002` is reported.
- **AC-2d.** Given a wrapped parameter list whose `)` follows the last
  parameter, when the owner is a method, constructor, local function,
  operator, delegate, or primary-constructor type, then one `ASWF002` is
  reported at the `)`. The same code with `)` on its own line is not reported.
- **AC-2e.** Given a wrapped `new Type(...)` or target-typed `new(...)`
  argument list, or a constructor initializer (`: base(...)`), when `)` shares
  a line with other content, then `ASWF002` is reported.
- **AC-2f.** Given a wrapped call whose last argument is a block-bodied lambda
  closed by `})`, when analyzed, then `ASWF002` is reported, because `)` is
  not the first token on its line.
- **AC-2g.** Given a wrapped `if`, `while`, `for`, `foreach`, `switch`,
  `using`, `lock`, `catch`, `when`, `fixed` or parenthesized expression whose
  `)` shares a line with other content, then no `ASWF002` is reported: only
  invocations, object creations and declarations are governed.
- **AC-2h.** Given a `(` and `)` that are on different lines only because of a
  trailing comment after `(`, with `)` first on its line, then no `ASWF002` is
  reported.

### ASWF003: block nesting

- **AC-3a.** Given a method body, when blocks (`if`, `for`, `foreach`,
  `while`, `do`, `switch` statement, `using` statement, `lock`, `fixed`,
  `try`) nest two deep without a `try`, then no `ASWF003` is reported.
- **AC-3b.** Given three nested blocks none of which is a `try`, when
  analyzed, then one `ASWF003` is reported, located on the keyword of the
  third block.
- **AC-3c.** Given three nested blocks where one is a `try` (for example
  `foreach` > `if` > `try`, or `if` > `try` > `foreach`), when analyzed, then
  no `ASWF003` is reported.
- **AC-3d.** Given four nested blocks, one of them a `try`, when analyzed,
  then `ASWF003` is reported on the fourth.
- **AC-3e.** Given an `else if` chain, when analyzed, then each `else if`
  continues its `if` and does not add a level.
- **AC-3f.** Given `catch` and `finally` clauses of a `try`, when analyzed,
  then they belong to the `try`'s level and add none.
- **AC-3g.** Given a local function, lambda, anonymous method, or accessor
  nested in blocks, when analyzed, then depth counting restarts inside it, as
  Python's counting restarts in a nested function or lambda.
- **AC-3h.** Given a `using` declaration (`using Foo x = ...;`) or a `switch`
  expression, when analyzed, then neither counts as a block.

### ASWF004: nested expressions

- **AC-4a.** Given `Outer(Inner(x))`, when analyzed, then no `ASWF004` is
  reported: one call inside one call is the ceiling.
- **AC-4b.** Given `Outer(Middle(Inner(x)))`, when analyzed, then one
  `ASWF004` is reported on `Inner(x)`.
- **AC-4c.** Given a fluent chain `a.B().C().D()`, or `Outer(x.Inner().Chain())`
  where `Inner` is the receiver, not an argument, when analyzed, then no
  `ASWF004` is reported: a receiver is not a nesting level.
- **AC-4d.** Given object creations, `Outer(new Middle(Inner(x)))`, when
  analyzed, then `ASWF004` is reported on `Inner(x)`: `new` with arguments
  counts as a call.
- **AC-4e.** Given a LINQ query expression, when a call inside it sits in
  another call's argument, then the query counts as one level, as a
  comprehension does in Python.
- **AC-4f.** Given an expression-bodied lambda inside an argument, such as
  `Outer(() => Middle(Inner(x)))`, when analyzed, then depth continues
  through the lambda and `ASWF004` is reported on `Inner(x)`; given a
  block-bodied lambda, then counting stops at the first statement in the body.
- **AC-4g.** Given `nameof(x)` as an argument at any depth, when analyzed,
  then it is not counted as a call.

### ASWF005: boolean chains

- **AC-5a.** Given `foo && bar` or `foo || bar` on one line, when analyzed,
  then no `ASWF005` is reported.
- **AC-5b.** Given a chain of three or more operands of the same operator
  sharing a line (`foo && bar && bat`), when analyzed, then one `ASWF005` is
  reported on the whole chain, and its message names the operand count.
- **AC-5c.** Given a chain of three or more where every operator is the first
  token on its line, as in `return foo` / `&& bar` / `&& bat;`, then no
  `ASWF005` is reported. The first operand may share a line with `return`,
  `=`, or `(`.
- **AC-5d.** Given a chain of three or more with a trailing operator
  (`foo &&` / `bar &&` / `bat`), when analyzed, then `ASWF005` is reported.
- **AC-5e.** Given a mixed expression `a && b || c`, when analyzed, then each
  operator's chain is counted separately (two operands each) and no `ASWF005`
  is reported; `a && b && c || d` is reported for the `&&` chain.
- **AC-5f.** Given a bitwise `&` or `|` chain, when analyzed, then it is not
  governed.

### ASWF006: no `Async` suffix

- **AC-6a.** Given a method, local function, or interface member declared in
  our source whose name ends in `Async` (ordinal, case-sensitive), when
  analyzed, then one `ASWF006` is reported at its identifier.
- **AC-6b.** Given a method whose name does not end in `Async` (including
  `AsyncRunner` or `Run_WhenAsyncFails`), when analyzed, then no `ASWF006` is
  reported.
- **AC-6c.** Given a method that overrides, or implements (implicitly or
  explicitly), a member declared outside the compilation (for example
  `IAsyncDisposable.DisposeAsync`), when analyzed, then no `ASWF006` is
  reported, because its name is not ours to choose.
- **AC-6d.** Given a method that implements or overrides a member declared in
  our own source whose name ends in `Async`, when analyzed, then `ASWF006` is
  reported on the declaration as well as on the original.
- **AC-6e.** Given a call to a framework method such as
  `File.ReadAllTextAsync(...)`, when analyzed, then no `ASWF006` is reported:
  only declarations are checked.

## Out of scope

- House rule 4 (one expression per line), rule 3 (method length), and any
  other house rule not listed above.
- Code fixes, refactorings, or IDE quick-fix providers for the diagnostics.
- Checking that the closing `)` is aligned with the statement that opened it.
- Reading `max_line_length` or `csharp_wrap_before_*_rpar` from
  `.editorconfig`; the limits are constants in the analyzer.
- The Python rules E9002, E9003 and E9004, and changing any
  `.editorconfig` severity.
- Analyzing the analyzer project's own source with the analyzers it defines
  (a project cannot reference its own output as an analyzer); its code is
  held to the standards by review and by the test project's coverage.
- Mutation testing and publishing the analyzer as a NuGet package.

## Decisions

- **IDs.** `ASWF001` to `ASWF006` is a new prefix; the item gave no IDs, and
  the canary needs stable names for `build:<ID>`.
- **Project names.** `src/AgenticSoftwareWorkflow.Analyzers` and
  `tests/AgenticSoftwareWorkflow.Analyzers.Test` follow the existing
  `<Solution>.<Area>` and `.Test` naming.
- **Limits are constants.** 120 characters is hard-coded rather than read from
  `.editorconfig`, so the rule cannot be weakened by editing configuration.
- **Strict `)` rule.** A closing `})` after a block-bodied lambda is reported,
  as the old lexical check did; the standard says `)` closes on its own line
  with no exception.
- **Block nesting mirrors E9003.** The block itself counts; depth over 2
  (counting non-`try` blocks), or over 3 counting everything, is reported.
  Lambdas and local functions restart counting, like Python scopes.
- **Nested expressions mirror E9002.** Only argument positions and query
  expressions are levels; receivers are not. `nameof` is exempt because it is
  not a call at run time. Object creation counts as a call because Python
  constructors are calls.
- **Boolean chain first operand.** Unlike E9004, the first operand need not
  start its line, because the standard's own example is `return foo` followed
  by `&& bar` lines. Only `&&` and `||` are governed.
- **Async suffix scope.** "Framework names are exempt" is implemented as
  exempting declarations that override or implement a member declared outside
  the compilation, since those names cannot be changed; declarations only,
  so calls to framework `...Async` methods are untouched.
- **Generated code is skipped**, so source generators and designer files do
  not break the build.
- **Existing code is made compliant in this item**, since the analyzers are
  errors in every project and AC-4 requires a green gate.
- **`scripts/csharp_parens.py`** is deleted only if nothing else imports it;
  otherwise it stays and only its docstring reference is updated.
