# Sandbox what workers run

## Summary

Roles that may run `dotnet build`, `dotnet test` or `dotnet format`
(`WorkflowRoles.TestAuthor` and `WorkflowRoles.Implementer`) execute
worker-written code as the maintainer's WSL user. That code can read
`~/.config/gh`, Claude Code's credentials and SSH keys, and can reach the
network. This item turns on Claude Code's own OS-level sandbox for those
roles' Bash commands. The sandbox settings are generated by
`ClaudePermissionSettings` and passed inline with `--settings`, next to the
permission rules the adapter already passes. Child processes of a Bash
command, such as the test host started by `dotnet test`, inherit the sandbox.
A live check proves that a worker cannot read `~/.config/gh/hosts.yml` and
cannot open a network connection.

## Acceptance criteria

- **AC-1**: Given a role whose `AgentAccess` has at least one allowed
  command, when `ClaudePermissionSettings.For(access)` is called, then the
  returned JSON has a top-level `sandbox` object next to `permissions`, and
  `sandbox.enabled` is `true`.
- **AC-2**: Given the same access, when the settings are produced, then
  `sandbox.failIfUnavailable` is `true`. If the sandbox cannot start (for
  example `bubblewrap` is missing), the run fails instead of running
  commands unsandboxed.
- **AC-3**: Given the same access, when the settings are produced, then
  `sandbox.allowUnsandboxedCommands` is `false`. A command cannot opt out of
  the sandbox.
- **AC-4**: Given the same access, when the settings are produced, then
  `sandbox.network.allowedDomains` is an empty array and
  `sandbox.network.allowLocalBinding` is `false`. No domain, including
  `nuget.org` and `github.com`, is reachable.
- **AC-5**: Given the same access, when the settings are produced, then
  `sandbox.filesystem.denyRead` contains `~/`, and
  `sandbox.filesystem.allowRead` contains exactly `~/.nuget` and `~/.dotnet`.
  Nothing else in the home directory is readable, including `~/.config/gh`,
  `~/.claude` and `~/.ssh`.
- **AC-6**: Given the same access, when the settings are produced, then
  `sandbox.filesystem.allowWrite` contains no path under `~/` other than
  `~/.nuget` and `~/.dotnet`. The working directory and the temporary
  directory remain writable through Claude Code's defaults.
- **AC-7**: Given the same access, when the settings are produced, then
  `sandbox.autoAllowBashIfSandboxed` is `false` or absent. The command
  allow-list in `permissions.allow` still decides which commands run.
- **AC-8**: Given a role whose `AgentAccess` has allowed commands, when the
  settings are produced, then `permissions.allow` and `permissions.deny` are
  exactly what they were before this item. The sandbox adds protection and
  removes none.
- **AC-9**: Given a role with no allowed commands and no path rules
  (`AgentAccess.ToolsOnly`), when the settings are produced, then the result
  is `Option<string>.None`. Roles that cannot run Bash get no sandbox
  settings.
- **AC-10**: Given a role with path deny rules but no allowed commands, when
  the settings are produced, then the JSON contains no `sandbox` object.
  The sandbox is tied to the ability to run commands.
- **AC-11**: Given `WorkflowRoles.TestAuthor` and `WorkflowRoles.Implementer`,
  when `ClaudeCodeAgentRunner` builds their invocations, then the
  `--settings` argument for each contains the sandbox settings of AC-1 to
  AC-7. This test goes through the runner, not only through
  `ClaudePermissionSettings`.
- **AC-12**: Given a new live test `SandboxLiveTest`, marked `Explicit` with
  `[Trait("Category", "Live")]` so `scripts/live-checks.sh` runs it, when an
  Implementer run is told to read `~/.config/gh/hosts.yml` with the Read
  tool and with `cat` in Bash, then the answer does not contain the file's
  contents. The test first asserts that the file exists and fails with a
  message saying so if it does not, because a missing file would prove
  nothing.
- **AC-13**: Given the same live test class, when an Implementer run is told
  to open a TCP connection to a listener the test has opened on `127.0.0.1`,
  then the listener accepts no connection within the test's timeout.
- **AC-14**: Given the same live test class, when an Implementer run is told
  to run `dotnet build` on a minimal console project in its workspace, then
  the build succeeds. This positive control proves the sandbox is not so
  tight that no worker could do its job. The project must need no package
  download.
- **AC-15**: Given the live tests of AC-12 and AC-13, when each run
  completes, then the result's `DeniedTools` is not empty or the failed
  command's refusal is visible in the answer, so a run where the model never
  tried cannot pass. This follows the pattern of
  `SeparationOfAuthorityLiveTest`.
- **AC-16**: Given `scripts/live-checks.sh` is run, when it finishes, then
  `SandboxLiveTest` was among the tests executed.
- **AC-17**: Given `docs/how-it-works/architecture.md`, when this item is
  done, then it says that worker commands run inside Claude Code's sandbox,
  names what the sandbox withholds (credentials in the home directory and
  the network), and states that a worker run fails if the sandbox is
  unavailable. Any C# shown comes from tests via `mdsnippets`.

## Out of scope

- A container per worker run. Claude Code's sandbox is the chosen mechanism
  (see Decisions).
- Environment variables. If the conductor's own environment holds a token
  such as `GH_TOKEN`, the sandbox does not hide it from child processes.
  Scrubbing the worker's environment is a separate item.
- Sandboxing the conductor's own `gh`, `git` and `dotnet format` runs
  outside a worker.
- Restoring NuGet packages for a worker. Restores that need the network fail
  inside the sandbox.
- Sandboxing roles that cannot run Bash.
- Changing any role's tools, allowed commands or path rules.

## Decisions

- **Mechanism**: Claude Code's sandbox, not a container. It needs no new
  runtime, and the adapter already passes `--settings`. It is OS-level
  (`bubblewrap` on Linux and WSL2), so it covers child processes such as the
  test host. AC-12 to AC-14 verify that claim on the real tool. If they
  show it does not hold, this item must be revisited, not weakened.
- **Fail closed**: `failIfUnavailable` is `true` and
  `allowUnsandboxedCommands` is `false`. A missing sandbox stops the run
  instead of silently dropping the protection.
- **No network at all**, including `nuget.org`. The issue asks for a sandbox
  that "cannot reach the network", and any allowed domain could carry data
  out. The cost is that a worker cannot add a package that is not already in
  `~/.nuget/packages`. Restores from that cache work offline. Such a package
  must be restored by a maintainer first.
- **Deny the whole home directory, allow two subdirectories**: a deny-list of
  known credential files would miss the next tool's token. `~/.nuget` and
  `~/.dotnet` are re-allowed because `dotnet` fails without them. They hold
  no credentials in this setup. A `NuGet.Config` with feed passwords would
  be exposed to the worker, which is a known limitation.
- **Sandbox only for roles that can run commands**: the other roles have no
  Bash tool, so there is nothing to sandbox. This keeps the existing
  `ToolsOnly` behaviour (AC-9) unchanged.
- **Setting names** (`sandbox.enabled`, `failIfUnavailable`,
  `allowUnsandboxedCommands`, `network.allowedDomains`, `allowLocalBinding`,
  `filesystem.denyRead`, `allowRead`, `allowWrite`, `autoAllowBashIfSandboxed`)
  follow Claude Code's documented sandbox settings. If the installed Claude
  Code version names one differently, the live checks decide, and AC-1 to
  AC-7 are corrected to the real names.
- **Loopback listener for the network check**: it proves the block without
  depending on the internet. It also avoids sending anything to an outside
  host.
- **Real `hosts.yml` in the live check**: the issue names that file. The test
  never prints or stores its contents. It only checks that they do not
  appear in the answer.
- **`autoAllowBashIfSandboxed` stays off**: the sandbox adds a boundary but
  does not replace the command allow-list.
