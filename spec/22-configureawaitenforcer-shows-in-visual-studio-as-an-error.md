# Specification: adopt ConfigureAwait.Fody (issue #22)

## Summary

The Visual Studio extension rule `ConfigureAwaitEnforcer` reports "Consider using ConfigureAwait(false)" as an error on every `await` (for example `CommandLine.cs` lines 46, 51 and 59). The extension is not part of this repo, so `dotnet build` and `scripts/gates.sh` never see it. The maintainer has decided to adopt `ConfigureAwait.Fody`, so that every `await` in every project is woven to `ConfigureAwait(false)` at compile time. This keeps the rule meaningful for other C# projects this workflow builds. The change adds the package, pins it centrally, and declares `[assembly: ConfigureAwait(false)]` once for all projects. It must also prove that the 100% line and branch coverage gate still measures correctly under IL weaving. Finally it records, in the docs and `.editorconfig`, how the rule is handled at build time and in the IDE.

## Acceptance criteria

1. Given `Directory.Packages.props`, when it is read, then it contains exactly one `PackageVersion` entry for `ConfigureAwait.Fody` with an exact, non-floating version. It also has a one-line XML comment explaining why the package is used, in the style of the neighbouring entries.
2. Given every `.csproj` in the repo (`src/AgenticSoftwareWorkflow.Cli`, `src/AgenticSoftwareWorkflow.Conductor`, `tests/AgenticSoftwareWorkflow.Conductor.Test`, `tests/AgenticSoftwareWorkflow.TestProcess`, `tests/StyleCanary`), when it is built, then the assembly has `ConfigureAwait(false)` declared at assembly level. The declaration is made in one shared place (`Directory.Build.props` or an equivalent single file), not copy-pasted per project. No `.csproj` carries a `Version` attribute on the `ConfigureAwait.Fody` reference.
3. Given the built `AgenticSoftwareWorkflow.Cli` and `AgenticSoftwareWorkflow.Conductor` assemblies, when their async state machines are inspected (for example by a test that reflects over the IL, or one that runs an `await` and checks the continuation is not marshalled back to a captured `SynchronizationContext`), then the awaits are woven to `ConfigureAwait(false)`. A test must fail if the weaving is removed.
4. Given a test that sets a `SynchronizationContext` which records `Post` calls and then awaits a genuinely asynchronous operation in production code, when the code under test completes, then the context received no `Post` for the continuation (proves the Fody behaviour end to end).
5. Given `scripts/gates.sh` run from WSL, when the Fody weaver is active, then the whole script passes, including the build with `TreatWarningsAsErrors`, all tests, and the 100% line **and** branch coverage threshold, with the threshold unchanged. Coverage must not drop because of weaver-generated code. If the weaver makes coverage unmeasurable or below 100%, work stops and the problem is reported. The threshold, gate or rule is not lowered, excluded or weakened.
6. Given the committed repository, when `FodyWeavers.xml` is needed by the package, then it is committed with the minimum content required (or generated by the build and ignored consistently with the existing `.gitignore` entry for `FodyWeavers.xsd`). A clean checkout builds without a manual step.
7. Given the build-time analyzer search, when the work is done, then `docs/contribute/coding-standards.md` states the result: whether any build-time analyzer understands Fody's assembly attribute (CA2007 does not). If none does, the expected outcome, then CA2007 is not enabled as an error and any build-time ConfigureAwait rule that fires is suppressed globally. That suppression lives in `.editorconfig` with a comment explaining that source analyzers cannot see Fody's post-compile weaving. If one does, it is enabled as a build error and a violation for it is added to `tests/StyleCanary`, so `scripts/gates.sh verify` proves it fires.
8. Given a build with Fody active, when `dotnet build` runs, then no new CA2007 or other ConfigureAwait warning appears. A suppression is added only if one does appear, and it carries a comment (the repo rule: every suppression is explained).
9. Given the "No `ConfigureAwait` noise" bullet in `docs/contribute/coding-standards.md` (lines ~218–224), when this item is done, then the bullet is rewritten. It no longer says `ConfigureAwait(false)` is "not written" and reserves Fody for libraries. It says that Fody with one assembly-level attribute is the repo-wide mechanism, that `ConfigureAwait(false)` is still never written by hand at an `await`, and why. Any C# shown in documentation comes from tests via `mdsnippets`, not typed by hand.
10. Given Visual Studio with the `ConfigureAwaitEnforcer` extension, when the maintainer rebuilds the solution after the change, then the `ConfigureAwaitEnforcer` errors for `CommandLine.cs` are gone. This is verified by the maintainer only, because the extension is the only reporter. The pull request description asks for that confirmation and records the result. If the errors persist, the follow-up is the global `.editorconfig` suppression (`dotnet_diagnostic.ConfigureAwaitEnforcer.severity = none`) with an explanatory comment, which the maintainer's Fody experience predicts.
11. Given any non-test `await` in `src/`, when the change is complete, then no production source file has been edited to add `.ConfigureAwait(false)` by hand.

## Out of scope

- Writing `ConfigureAwait(false)` manually in source.
- Adopting CA2007 as an error across the repo.
- Changing coverage thresholds, gate definitions, or the Maintainer approval check.
- Making the IDE extension itself a CI gate (it is not installable in CI).
- Changes to `spec/`, `.github/`, `scripts/maintainer_approval.py` or `aswf.json`.

## Decisions

- **All projects, including test projects, get the attribute.** The IDE rule fires in every project, and one shared declaration is simpler than a per-project opt-in. If a particular project (for example `StyleCanary`) cannot be woven, the implementer reports it rather than silently excluding it.
- **Package version.** The specification does not name a version. The implementer pins the latest stable version compatible with net10.0, exactly.
- **Single shared declaration.** The mechanism (an `AssemblyAttribute` item or a source file linked from `Directory.Build.props`) is left to the implementer, as long as it exists in one place.
- **Suppression is conditional.** Criteria 7, 8 and 10 encode the maintainer's stated expectation (Fody plus a documented global suppression) as a fallback. The analyzer search outcome decides which branch applies, and it is documented either way.
- **Criterion 4 is the behavioural proof of weaving**, in addition to criterion 3, because IL inspection alone can be brittle. The implementer may satisfy criterion 3 with this test if it fails when weaving is removed.
